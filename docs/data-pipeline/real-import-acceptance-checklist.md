# Real Import Acceptance Checklist

Date: 2026-07-03
Owner: QA / Release Gate
Scope: acceptance criteria for moving from import-test JSON to formal real product batch import

## Purpose

Use this checklist after generating `outputs/cms-facts-import-test.json` and before replacing the active real product source. The import artifact must stay facts-only and must pass the same adapter, domain, SEO, GEO, boundary, scale, and build gates used by the release process.

## Data Shape Gate

The import artifact must be a `CmsFactInput` object with only these top-level arrays:

- `categoryFacts`
- `productFacts`

Reject the batch if any generated, runtime, route, or projection field appears in the import payload. Forbidden fields include:

- `slug`
- `canonical`
- `canonicalPath`
- `slugPath`
- `categoryPath`
- `breadcrumb`
- `depth`
- `children`
- `seo`
- `localizedSeo`
- `jsonLd`
- `jsonld`
- `jsonLD`
- `geo`
- `geoAi`
- `localizedGeoAi`
- `geoEntity`
- `identity`
- `classification`

These values are generated by the adapter, SEO, GEO, or runtime layers. They must not be authored by Strapi, Excel, CSV, or import transforms.

## Identity Gate

Each product row must satisfy all identity checks before import acceptance:

- `product_id` maps to `productFacts[].id`, starts with `prd_`, and is unique across the new batch and existing real catalog.
- `sku` is present and unique across the new batch and existing real catalog.
- `model` is present and produces a unique generated model slug; models that differ only by case, spacing, underscore, punctuation, or separator normalization are treated as collision risks.
- `family` is present and is either `sensor` or `valve`.
- `series_id`, when present, starts with `ser_` and is used as a family/series hint only, not as a replacement for `family`.

## Category Gate

Every product must point at a known category:

- `primary_category_id` / `primaryCategoryId` / `core.primaryCategory` must exist in `categoryFacts[].id`.
- Each `additionalCategoryIds[]` value must exist in `categoryFacts[].id`.
- `categoryFacts` must contain exactly one root with `parentId: null`.
- Category parent references must not create cycles.
- Adapter-derived category depth must remain at or below 4.
- Sibling category names must generate unique slugs.

## Family Profile Gate

Sensor and valve products have different required fact profiles.

For `sensor` products:

- Provide `sensorProfile` with non-empty `measurements` and `outputs`, or provide the legacy top-level `measurements` and `outputs` accepted by the adapter.
- Each sensor measurement must include `range` and `overloadLimit`.
- Each sensor output must include `kind` and `value`.
- Sensor `measurementKinds` must match the measurement rows.
- Sensor environmental facts should include compatible media, wetted materials, and at least one media or ambient temperature limit.

For `valve` products:

- Provide `valveProfile`.
- `valveProfile.pressureRating`, `connection`, `material`, `mode`, `compatibleMedia`, and `size` must be present.
- Valve products do not need `measurements`, `outputs`, or electrical connection facts unless the product is intentionally modeled as a sensor.
- Valve `measurementKinds` should normally be empty.

## Optional Fact Degradation

These fields are optional at the adapter boundary but affect output quality and governance:

- `documents`: Optional technically, but real import acceptance should treat at least one datasheet or catalog as expected for each product when available. Without documents, GEO evidence must degrade to generated facts without fabricated `source-backed` refs.
- `assets`: Optional technically. Without assets, product listing and detail views must render without images and must not invent product imagery.
- `certifications`: Optional. Missing certification facts must not block import, but certified claims must not appear in copy, specifications, SEO, or GEO unless the code is provided.
- `commercialTerms`: Optional. Missing MOQ, lead time, warranty, OEM, or private-label facts must degrade to quote/contact flows, not placeholder claims.

A product can enter import testing with optional fields missing only when the generated UI, SEO, and GEO output remains truthful and readable.

## SEO / GEO Generation Gate

The import artifact must not contain SEO, JSON-LD, canonical, or GEO fields. After adapter conversion, the release gates must confirm generation:

- `validate:seo` confirms generated title, meta description, h1, canonical path, hreflang, sitemap entries, and Product JSON-LD.
- `validate:geo` confirms generated product feed, GEO index, all-products AI-readable output, answer blocks, `llms.txt` links, evidence fallback behavior, and sensor + valve readable fixture coverage.
- Sensor and valve products must both produce readable output. For the current release gates, fixture coverage proves both families; after real valve import, the real data stats must show valve products are present and the same gates must be rerun.

## Search Acceptance Gate

After import testing, the catalog must be searchable through the domain product index and public product list behavior. For a representative sample of sensor and valve products, verify hits by:

- Industry: `industryIds` filter returns the expected products.
- Application: `applicationIds` filter returns the expected products.
- Media: compatible media terms from `environmentalLimits.compatibleMedia`, `sensorProfile.environmentalLimits.compatibleMedia`, or `valveProfile.compatibleMedia` are present in searchable text.
- Model: the exact model and normalized model tokens return the product.
- Family: `sensor` and `valve` family filters return the expected products.

A formal batch should not proceed if the imported data cannot be discovered by buyer-facing industry, application, medium, model, and family paths.

## Required Commands

If `outputs/cms-facts-import-test.json` exists, run:

```powershell
npm run validate:cms-facts -- --file outputs\cms-facts-import-test.json
```

Always run:

```powershell
npm run lint
npm run typecheck
npm run validate:boundaries
npm run validate:domain
npm run validate:seo
npm run validate:geo
npm run validate:scale-1000
npm run build
```

Use `npm run validate:cms-facts -- --file outputs\cms-facts.json` as the current real-data stats probe when updating the release gate status.

## Go / No-Go Rule

Formal batch import is allowed only when all of these are true:

- The import-test JSON exists and passes `validate:cms-facts` with exit `0`.
- All required release gate commands exit `0`.
- Current real-data counts and import-test counts are recorded in `docs/current-release-gate-status.md`.
- No generated fields are present in the import artifact.
- Real product statistics match the import plan, including expected sensor and valve counts.
- Any missing optional facts have an explicit degradation path and do not create false UI, SEO, GEO, certification, evidence, or commercial claims.

If any required command exits non-zero, or if the import artifact lacks expected real valve data for a valve batch, the decision is no-go until the data or validation issue is corrected and the full gate sequence is rerun.
