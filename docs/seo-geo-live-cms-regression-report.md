Date: 2026-06-25
Role: Thread 3 SEO/GEO Runtime
Scope: Public SEO/GEO runtime stability after real CMS facts ingress

## Verdict

SEO/GEO remains stable for real CMS facts integration when CMS data enters only through the Domain-normalized runtime path.

The approved source path is unchanged:

```txt
lib/cms/products.ts
  -> lib/runtime/domain-products.ts
  -> lib/seo/* and lib/geo/*
  -> public SEO/GEO routes
```

No page UI, Strapi adapter, CMS data structure, or public route response shape was changed for this regression pass.

## Regression Boundary Checked

Reviewed public runtime surfaces:

- `app/sitemap.ts`
- `app/robots.ts`
- `app/llms.txt/route.ts`
- `app/api/product-feed/route.ts`
- `app/api/geo/index/route.ts`

- `app/api/geo/answers/route.ts`

The reviewed SEO/GEO route handlers call SEO/GEO builders or the runtime Domain facade. They do not import `lib/cms/*`, adapter modules, raw CMS facts, Strapi transport modules, or public CMS/Strapi/facts environment variables.

`lib/runtime/domain-products.ts` remains the only product runtime facade below SEO/GEO. Its upstream dependency is `lib/cms/products.ts`, and its public output is limited to Domain-normalized product records, category tree/catalog projections, list projections, and safe source metadata.

## SEO Output Stability

Confirmed source policy:

- `sitemap` is generated from runtime Domain product records, localized static entries, industry entry view models, and application entry view models.
- `robots` is generated from site configuration and canonical sitemap URL; it is CMS-independent.
- `canonical` URLs are derived from Domain product SEO canonical paths and configured site origin.
- `hreflang` maps are derived from `next-intl` routing locales plus Domain product SEO paths.
- Product JSON-LD is generated from `ProductDetailPageData` and Domain product identity/specification fields.
- FAQPage JSON-LD is generated from Domain product detail data and Domain-derived FAQ items.

No SEO output directly reads Strapi, raw CMS response envelopes, raw facts, relation wrappers, draft state, or generated CMS SEO fields.

## GEO Output Stability

Confirmed source policy:

- `llms.txt` is generated from Domain products, industry/application entry view models, and public feed/GEO endpoint URLs.
- `product-feed` is generated by `buildGeoProductFeed(locale)` from runtime Domain records.
- `geo/index` is generated by `buildGeoIndex(locale)` from runtime Domain records and Domain entry view models.
- `geo/products` maps `getRuntimeDomainProductRecords()` through `buildAiReadableIndustrialProduct`.
- `geo/answers` is generated by `buildGeoAnswerBlocksDocument(locale)` from product and application Domain projections.
- AI-readable product blocks keep evidence refs and facts tied to Domain product fields, not hidden or fabricated AI content.

No GEO output directly reads Strapi, raw CMS response envelopes, raw facts, relation wrappers, draft state, or generated CMS GEO fields.

## Executable Assertion Adjustment

The real CMS dry-run sample contains only two products. That exposed a validator-only payload budget issue in `scripts/validate-geo.mjs`: `geo/index` has fixed discovery overhead for endpoints, industries, and applications, but the previous budget was purely `productCount * bytesPerProduct`.

The executable assertion was tightened to model that fixed overhead with a minimum of `3` budget units for `geo/index` payload validation. This change affects only validation math for small real-facts samples and does not change any public GEO document shape, route handler, or Domain output.

## Public Route Contract Decision

The public route contract remains unchanged:

- `GET /sitemap.xml` keeps the existing sitemap shape.
- `GET /robots.txt` keeps the existing robots shape.
- `GET /llms.txt` keeps the existing plain-text discovery shape.
- `GET /api/product-feed` keeps the existing JSON contract envelope and `geo-product-feed-v1` payload.
- `GET /api/geo/index` keeps the existing JSON contract envelope and `geo-index-v2` payload.
- `GET /api/geo/products` keeps the existing JSON contract envelope and `geo-products-v1` payload.
- `GET /api/geo/answers` keeps the existing JSON contract envelope and `geo-answer-blocks-v2` payload.

Real CMS cutover does not require shape changes in SEO/GEO routes as long as live data continues to normalize through `lib/cms/products.ts` and `lib/runtime/domain-products.ts` before reaching public builders.

## Risk Notes

- AI-readable summaries and evidence refs must continue to be derived from Domain fields only.
- CMS-generated SEO/GEO fields must not bypass Domain normalization.
- Raw Strapi envelopes, relation wrappers, upload internals, draft state, and transport errors must remain below `lib/cms/*`.
- If live CMS facts expand product copy or evidence fields significantly, the GEO payload budget assertions should be reviewed through `validate:geo`, not by changing public route shapes.
