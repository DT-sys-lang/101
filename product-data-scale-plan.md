# Product Data Scale Plan

## Scope

This plan defines the product data system boundary for growing from 300 products to 1000+ industrial sensor products. It does not define UI pages and does not implement Strapi. Strapi, CSV, PIM, or any future CMS should provide facts only. Domain records, SEO, GEO, category paths, slugs, and indexes are generated or validated at the domain/adapter boundary.

## Current Architecture Assessment

The current architecture is already close to the right shape for 300 to 1000+ products:

1. `ProductRecord` is the canonical product detail model.
2. `CategoryTree` is the canonical category model.
3. `ProductCatalogIndex` is a derived index for list/search/filter/detail resolution.
4. `adapter/product.adapter.ts` builds domain records from facts and rejects CMS-provided generated fields.
5. SEO and GEO are generated by adapters from source facts, not authored directly by CMS.

The main long-term gap is not the product object itself. The gap is the governed Specification Definition layer: product records contain specification values, but the system needs a global registry defining what each spec key means, how it is typed, which unit families it accepts, which categories it applies to, and how it should behave in filtering, comparison, search, parameter tables, datasheets, and AI/GEO summaries.

The current governance rulebook is captured in `product-parameter-governance.md` and should be treated as the authoritative explanation of the spec layer.

## Specification Governance Rules

- `SpecificationDefinition` is the registry entry for a governed parameter.
- `ProductSpecificationValue.key` must resolve to a known registry key when validation is enabled.
- `facet` means filterability, `comparison` means comparability, and searchability is derived by the catalog index from domain records.
- `appliesToCategoryIds` is the category scope contract.
- `geo.includeInFactTable` is the GEO eligibility contract.
- `allowedUnits` must stay within the declared `unitFamily`.
- `valueType` must match how the parameter is authored and validated.
- Group keys inside `ProductRecord.specificationGroups` are authoring buckets, not semantic identifiers.

## Scale Test Gate

The runnable scale gate is `npm run validate:scale-1000`. It generates 1000 raw CMS product facts without `slug`, `seo`, `jsonLd`, or `geoAi`, runs them through `adapter/product.adapter.ts`, and verifies they become domain `ProductRecord` objects.

For larger runs:

```bash
node --loader ./scripts/ts-import-loader.mjs ./scripts/generate-scale-cms-facts.mjs --count 600 --validate
node --loader ./scripts/ts-import-loader.mjs ./scripts/generate-scale-cms-facts.mjs --count 1000 --validate
```

Use `--out tmp/cms-facts-1000.json` to write a payload, then run `npm run validate:cms-facts -- --file tmp/cms-facts-1000.json`.

## Adapter Boundary

The adapter layer is correctly placed. It should remain responsible for converting external fact input into domain records.

External facts may provide:

- category id, parentId, localized name
- product id, sku, model, brand, lifecycle, availability
- category references
- localized content
- measurements
- outputs
- connections
- environmental limits
- raw specification values
- variants
- documents
- assets
- commercial terms

External facts must not provide:

- generated category slug
- generated category path
- slug path
- canonical path
- breadcrumb
- SEO fields
- JSON-LD
- GEO entity
- GEO profile
- product detail projections
- list/filter indexes

This boundary is expressed in `adapter/validation.ts` through `productSystemGeneratedFields`, `categorySystemGeneratedFields`, and strict allow-lists for `CategoryFact` and `ProductFact`.

## 300 to 1000+ Migration Plan

### Phase 1: Stabilize 300 Products

- Run `npm run validate:scale-1000` in CI as the first catalog scale gate.
- Introduce `SpecificationDefinition` registry.
- Normalize all existing spec keys.
- Add adapter validation that rejects unknown spec keys.
- Ensure all production product facts include measurements, overload limits, environmental limits, specifications, and datasheet documents.
- Keep `ProductCatalogIndex` generated per locale.

### Phase 2: Improve Selection and Comparison

- Add category-specific facet profiles.
- Add category-specific comparison profiles.
- Add normalized range values for pressure, temperature, level, current, voltage, and percent specs.
- Add variant-aware option matrix validation.
- Add source references to all comparison-critical specs.

### Phase 3: Datasheet and Evidence Automation

- Define datasheet section profiles from specification definitions.
- Link generated datasheets back into `ProductDocument`.
- Track document revision, source hash, and generated date.
- Require source-backed specs for GEO fact table fields.

### Phase 4: 1000+ Catalog Operations

- Split product facts by category or series for authoring convenience, but compile into one domain product source.
- Build locale indexes at build time or cache them server-side.
- Add quality gates for duplicate model slugs, duplicate SKUs, invalid category references, unknown spec keys, missing documents, and missing source refs.
- Track deprecated and replacement products with lifecycle and optional successor references.
- Keep specification governance in `product-parameter-governance.md` as the source of truth for parameter semantics.

## Final Recommendation

Keep the current `ProductRecord` and `CategoryTree` as the domain backbone. Do not expand them with every possible industrial parameter. Instead, add a governed `SpecificationDefinition` layer and use it to drive filtering, comparison, parameter tables, datasheets, and GEO facts. This keeps the core model stable while allowing the catalog to grow from 300 to 1000+ products without turning each product record into an unbounded custom object.

See `product-parameter-governance.md` for the governance matrix and extension workflow.
